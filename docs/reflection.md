# 反思

> 根據 [實際執行紀錄](run-log.md) 回答。

## 1. 哪一個節點最常出錯？

**「生成投影片」節點的失敗最多**（第一次完整檢查 13 張中有 4 張不通過），但**最該注意的是「Wiki 整理（concept 頁）」節點**。

- 4 張失敗的投影片裡，有 2 張的錯其實不是生成造成的，而是 concept 頁在整理時就出了問題：
  - 急診案例只搬了「31%、27%」這兩個結果，**漏掉了「40 次模擬、每次 12 小時」這個條件**，而且那一行沒有標來源 [S8]；
  - index 的來源表沒有作者與年份，簡報最後的參考資料頁就沒有根據。
- 生成節點本身的錯，則是「好心幫忙」型的：自己把 1.3B 換算成「13 億」、自己加上「約 15 分鐘」。內容不一定錯，但已經不是從 Wiki 來的了。
- 另外，**檢查器本身也會出錯**：第一版 check_slides 因為正規式只比對 `class="slide"`，漏掉了 `class="slide cover"` 的封面，所有編號都差 1。如果沒注意到「應該有 13 張卻只檢查到 12 張」，就會以為封面沒問題。

## 2. 發現問題後，把檢查往前移到哪一個步驟？

從「**簡報檢查**（check_slides）」往前移到「**Wiki 整理後的 lint**（lint_wiki v2）」：

| | v1 | v2 |
|---|---|---|
| lint_wiki | 只檢查結構（連結、孤兒頁、index、frontmatter） | ＋ 含數字的行必須有 `[S#]` |
| | | ＋ concept 頁的數字必須在被引用的來源頁找得到；來源頁的數字必須在 raw 卡片找得到 |

移過去之後馬上抓到 3 個問題，其中一個（`when-to-review.md` 第 10 行沒有 [S8]）正是第 11 張投影片失敗的根源。以後同類錯誤在 ingest 當下就會被擋下來，不用等到做簡報才發現。

**但也發現了限制**：lint 抓得到「寫了但沒來源／對不上」的數字，**抓不到「整理時漏掉的細節」**。「40 次、12 小時」被漏掉這件事，lint 不會報錯，只有在簡報想用它時才會發現。所以簡報檢查還是要留著，兩層檢查都需要。

## 3. 有沒有因此修改 workflow / graph？為什麼？

有，改了四個地方：

1. **lint 加入數字可追溯檢查**（上面說的）：錯誤越早抓，修正成本越低；在 Wiki 修一次，所有引用它的投影片都受益。
2. **新增「回到 Wiki」這條邊**：簡報檢查失敗時，先判斷根源在哪。根源在 Wiki 就回去修 Wiki，不在投影片上硬改。否則 Wiki 和簡報會越來越不一致，Wiki 就失去「知識庫」的意義。
3. **Schema（CLAUDE.md）新增規則**：「數字要連同條件一起搬」、「index 要有作者／年份」、「（綜合：說明）標記」。把這次學到的事寫進 schema，下一次 ingest 時 LLM 就會照做，這正是 LLM Wiki「人與 LLM 共同演進 schema」的用意。
4. **最後保留人工視覺檢查**：版面被撐開、文字被遮住這種問題，程式檢查完全看不到，必須靠人看截圖。

## 4. 心得

這次做的流程，剛好就是簡報在講的主題：**AI 生成內容時，人與檢查應該放在哪裡**。

- 不是每一步都要人看（太貴），而是把人放在「選題、確認大綱、最後看版面」這種**人做很快、AI 錯了代價很大**的位置；
- 能用程式檢查的（數字、來源）交給程式；
- 檢查器自己也會錯，所以「檢查結果的數量對不對」本身也值得看一眼。
